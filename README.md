# Bank Transaction Analytics and Fraud Detection

Big Data Analytics coursework project. A batch pipeline that processes **6.36 million
mobile-money transactions** with Apache Spark, finds where and when fraud happens, trains a
fraud detection model with Spark MLlib, and serves the results from MongoDB to a web dashboard.

**Stack:** Python + Apache Spark (Spark SQL, MLlib) + MongoDB + Machine Learning,
with Parquet for storage and FastAPI for the dashboard API.

**Live dashboard:** https://jayquery-007-bank-transaction-analytics.static.hf.space
(hosted on [Hugging Face Spaces](https://huggingface.co/spaces/JayQuery-007/bank-transaction-analytics))

## Problem

Banks and payment providers process millions of transactions a day, and only a tiny fraction
are fraudulent. The goals of this project are to:

1. Load a large transaction log into an analytics-friendly format.
2. Describe the data: which transaction types, times, amounts and accounts are involved in fraud.
3. Build a model that detects fraud far better than the provider's existing rule.
4. Make the results available through a database and a dashboard.

## Dataset

[PaySim — Synthetic Financial Datasets For Fraud Detection](https://www.kaggle.com/datasets/ealaxi/paysim1) (Kaggle, `ealaxi/paysim1`)

| | |
|---|---|
| Rows | 6,362,620 |
| Size | 494 MB CSV |
| Period | 744 hourly steps (31 days) |
| Fraud labels | 8,213 fraudulent transactions (0.13%) |

Real bank transactions can't be published for privacy reasons, so PaySim was generated by
an agent-based simulator calibrated on one month of real logs from a mobile money provider
in Africa. It is the standard public benchmark for transaction fraud detection.

| Column | Description |
|---|---|
| `step` | hour of the simulation (1–744) |
| `type` | CASH_IN, CASH_OUT, DEBIT, PAYMENT, TRANSFER |
| `amount` | transaction amount |
| `nameOrig`, `oldbalanceOrg`, `newbalanceOrig` | sender account and its balance before/after |
| `nameDest`, `oldbalanceDest`, `newbalanceDest` | receiver account and its balance before/after |
| `isFraud` | 1 if the transaction is fraudulent |
| `isFlaggedFraud` | 1 if flagged by the provider's existing rule (large transfers) |

## Architecture

```
 Kaggle CSV (494 MB)
        |
        v
 [1] spark_jobs/ingest.py        explicit schema, data quality checks, derived columns
        |
        v
 Parquet data lake               data/lake/transactions/type=*/   (315 MB, partitioned by type)
        |
        +--------------------------------+
        v                                v
 [2] spark_jobs/analytics.py     [3] spark_jobs/train_model.py
     Spark SQL aggregations           Spark MLlib: Logistic Regression vs Random Forest
        |                                |
        +---------------+----------------+
                        v
                MongoDB (bank_analytics)        serving layer: one collection per result set
                        |
                        v
                FastAPI (backend/app)  --->  dashboard (frontend/)
```

The full 6.36M rows stay in the Parquet lake. MongoDB holds only the query results the
dashboard needs: aggregates, model metrics and flagged transactions. This is the usual split
between a batch layer and a serving layer.

### Pipeline steps

| Step | What it does | Runtime* |
|---|---|---|
| `data/download_data.py` | downloads the dataset with `kagglehub` | ~20 s |
| `spark_jobs/ingest.py` | reads the CSV with an explicit schema, checks nulls/duplicates/invalid amounts, renames columns, adds `day`, `hour_of_day`, balance-error and `orig_emptied` columns, writes Parquet partitioned by `type` | ~20 s |
| `spark_jobs/analytics.py` | 7 Spark SQL queries (overview, type summary, hourly/daily activity, amount bands, balance patterns, repeat fraud destinations) published to MongoDB | ~25 s |
| `spark_jobs/train_model.py` | trains and evaluates the models, computes feature importance and a threshold curve, saves the model and the flagged test transactions | ~2.5 min |

\*On a 16 GB Windows laptop, Spark `local[*]`.

`notebooks/eda.ipynb` contains the exploratory analysis behind these steps, with plots.

## Findings

- **Fraud only occurs in TRANSFER (0.77%) and CASH_OUT (0.18%)** transactions. The other
  three types have no fraud at all. Frauds follow a take-over pattern: transfer the victim's
  balance to a controlled account, then cash it out.
- **The existing rule (`isFlaggedFraud`) flagged only 16 of 8,197 frauds** (0.2%).
- **Fraud volume is constant through the day** (about 270–370 per hour slot), while
  legitimate activity drops at night. As a result, **22% of transactions between 4:00 and
  6:00 are fraudulent**, compared with under 0.1% in business hours.
- **97.7% of frauds empty the sender's account**, compared with 42.7% of legitimate
  transfers/cash-outs. In 49.7% of frauds the receiver's recorded balance stays at 0 even
  though money arrived (0.06% for legitimate transactions).
- Fraud amounts are larger (median 442k vs 171k) and are capped at 10M: 287 frauds are
  exactly 10,000,000.
- **43 receiver accounts got more than one fraudulent transaction** (86 frauds). These are
  candidates for mule-account investigation.
- Data quality: no nulls or duplicates. 16 zero-amount rows (all CASH_OUT, all labelled
  fraud) were removed as invalid.

## Fraud detection model

Training data: 2.77M TRANSFER and CASH_OUT transactions (all other types have no fraud),
split 70/30 into training and test sets (seed 42).

Features: `is_transfer`, `amount`, sender and receiver balances before/after,
`error_balance_orig`, `error_balance_dest`, `hour_of_day`.

Fraud is 0.3% of this data, so accuracy is not meaningful: a model that never predicts fraud
is 99.7% accurate. The models are compared on precision, recall, F1 and area under the
precision-recall curve.

Results on the 831,437-row test set (2,407 frauds):

| Model | Precision | Recall | F1 | AUC-PR | Frauds caught | False alarms |
|---|---|---|---|---|---|---|
| Existing rule (`isFlaggedFraud`) | 1.000 | 0.002 | 0.003 | – | 4 / 2,407 | 0 |
| Logistic Regression (class-weighted) | 0.043 | 0.909 | 0.083 | 0.549 | 2,189 / 2,407 | 48,466 |
| **Random Forest** (60 trees, depth 12) | **0.993** | **0.998** | **0.995** | **0.998** | **2,401 / 2,407** | **17** |

- Logistic Regression catches most fraud, but with class weighting it raises about 20 false
  alarms for every real fraud. The relationship between balances and fraud is not linear.
- Random Forest is the selected model. The most important features are `new_balance_orig`
  (0.40), `error_balance_orig` (0.19) and `amount` (0.11).
- The 6 frauds it missed all have a sender balance recorded as 0 before and after, so the
  balance features carry no signal for them.
- Precision and recall stay above 0.99 for alert thresholds from 0.2 to 0.7, so the result
  isn't sensitive to the 0.5 cut-off.

## Running the project

Requires Python 3.10+.

### Dashboard only (works right after cloning)

The pipeline's results are committed in `results/` and the trained model in `models/`, so
the dashboard runs without downloading the data:

```bash
git clone https://github.com/JayQuery-007/bank_transaction_analysis.git
cd bank_transaction_analysis
python -m venv venv
venv\Scripts\activate            # macOS/Linux: source venv/bin/activate
pip install -r requirements.txt
python run.py
```

Open http://localhost:8000. The dashboard reads from MongoDB if it's running on
`localhost:27017` (override with `MONGO_URI`), otherwise from `results/*.json`.
The "Check a transaction" section loads the Spark model, so it needs Java 17.

### Full pipeline (rebuild everything from the raw data)

Needs **Java 17** (`JAVA_HOME` set, or `java` on the PATH) and a
[Kaggle API token](https://www.kaggle.com/settings) in `~/.kaggle/`. Alternatively, download
the CSV manually and save it as `data/raw/paysim.csv`.

```bash
python run_pipeline.py
```

Start MongoDB first if you want the results stored there. On Windows, `.\start.ps1` starts
a local MongoDB from `.\mongodb\` (if present) and then the dashboard.

### Deployment (Hugging Face Spaces)

The live dashboard is a **static** Hugging Face Space, which is free and needs no server.
`deploy/build_static.py` copies the frontend and `results/*.json` into `site/` and exports
the trained Random Forest's 60 trees from Spark's model files to JSON. `frontend/forest.js`
then scores transactions in the browser with the same logic as Spark MLlib. The build
checks the export against Spark's stored probabilities for all 2,424 scored test
transactions, and it matches exactly.

```bash
hf auth login                   # one-time, signs in to Hugging Face
python deploy/deploy_hf.py      # builds site/ and uploads it to the Space
```

For a server-based deployment (FastAPI + Spark + MongoDB), the repo also has a
`Dockerfile` (Python 3.11, Java 17, about 2 GB of RAM). It runs on any container host
such as Render, Railway or a VM. Docker Spaces on Hugging Face need a paid plan.

### Running Spark on Windows

Spark's local file writes call Hadoop native helpers (`winutils.exe`, `hadoop.dll`) on
Windows, which aren't distributed by Apache. Instead of downloading unofficial binaries, the
project includes a small Hadoop `FileSystem` subclass (`spark_jobs/winfs/src`, compiled into
`winfs.jar`) that uses plain Java file operations. `spark_jobs/common.py` enables it only
on Windows. The jobs also avoid Python UDFs, because PySpark's Python worker processes crash
on Windows with Python 3.12+.

## Limitations and future work

- PaySim is simulated. Its balance bookkeeping for fraudulent transactions is distinctive,
  which is why the balance-error features work so well. On real data, expect lower scores
  and more reliance on behavioural history.
- Customers almost never repeat in PaySim (6.35M distinct senders in 6.36M rows), so
  per-customer behaviour features (spending history, velocity) aren't possible here.
- The pipeline is batch. A natural extension is streaming new transactions through Kafka
  and scoring them with Spark Structured Streaming using the saved model.
- Runs on Spark in local mode; the same jobs would run unchanged on a cluster with the data
  in HDFS or object storage.
