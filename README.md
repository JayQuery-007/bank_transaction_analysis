# Bank Transaction Analytics and Fraud Detection

A batch pipeline that processes **6.36 million
mobile-money transactions** with Apache Spark, finds where and when fraud happens, and trains a
fraud detection model with Spark MLlib. On top of the results sits a web application with
**millisecond transaction search**, **fraud case management (full CRUD)** and **CSV upload with
batch scoring**.

**Stack:** Python + Apache Spark (Spark SQL, MLlib) + MongoDB + Machine Learning,
with Parquet for storage, DuckDB for fast search and FastAPI for the API.

**Live dashboard (read-only showcase):** https://jayquery-007-bank-transaction-analytics.static.hf.space
(hosted on [Hugging Face Spaces](https://huggingface.co/spaces/JayQuery-007/bank-transaction-analytics)).
The full application (search, cases, upload) needs a server and a database, so it runs locally
(`python run.py`) or from the Docker image; see [Hosting](#hosting).

## Problem

Banks and payment providers process millions of transactions a day, and only a tiny fraction
are fraudulent. The goals of this project are to:

1. Load a large transaction log into an analytics-friendly format.
2. Describe the data: which transaction types, times, amounts and accounts are involved in fraud.
3. Build a model that detects fraud far better than the provider's existing rule.
4. Make the results available through a database and a dashboard.

## Dataset

[PaySim — Synthetic Financial Datasets For Fraud Detection](https://www.kaggle.com/datasets/ealaxi/paysim1) (Kaggle, `ealaxi/paysim1`)

| | |
|---|---|
| Rows | 6,362,620 |
| Size | 494 MB CSV |
| Period | 744 hourly steps (31 days) |
| Fraud labels | 8,213 fraudulent transactions (0.13%) |

Real bank transactions can't be published for privacy reasons, so PaySim was generated by
an agent-based simulator calibrated on one month of real logs from a mobile money provider
in Africa. It is the standard public benchmark for transaction fraud detection.

| Column | Description |
|---|---|
| `step` | hour of the simulation (1–744) |
| `type` | CASH_IN, CASH_OUT, DEBIT, PAYMENT, TRANSFER |
| `amount` | transaction amount |
| `nameOrig`, `oldbalanceOrg`, `newbalanceOrig` | sender account and its balance before/after |
| `nameDest`, `oldbalanceDest`, `newbalanceDest` | receiver account and its balance before/after |
| `isFraud` | 1 if the transaction is fraudulent |
| `isFlaggedFraud` | 1 if flagged by the provider's existing rule (large transfers) |

## Architecture

```
 Kaggle CSV (494 MB)
        |
        v
 [1] spark_jobs/ingest.py        explicit schema, data quality checks, derived columns
        |
        v
 Parquet data lake               data/lake/transactions/type=*/   (315 MB, partitioned by type)
        |
        +--------------------------------+
        v                                v
 [2] spark_jobs/analytics.py     [3] spark_jobs/train_model.py
     Spark SQL aggregations           Spark MLlib: Logistic Regression vs Random Forest
        |                                |
        +---------------+----------------+
        |               |                |
        v               v                v
 [4] serving/       MongoDB (bank_analytics)        results/*.json
     build_search_  - result sets (read-only)        (committed copy of
     index.py       - cases, upload batches           every result set)
     DuckDB index     (read/write, per browser)
        |               |
        +-------+-------+
                v
        FastAPI (backend/app)  --->  dashboard (frontend/)
```

The full 6.36M rows stay in the Parquet lake. MongoDB holds only what the application needs:
the result sets, and the operational data users create (cases, upload batches). A DuckDB file
(`data/search.duckdb`, 878 MB, built from the lake in about 40 s) indexes every transaction by
sender, receiver and id, which is what makes search take milliseconds. This is the usual split
between a batch layer and a serving layer.

### Pipeline steps

| Step | What it does | Runtime* |
|---|---|---|
| `data/download_data.py` | downloads the dataset with `kagglehub` | ~20 s |
| `spark_jobs/ingest.py` | reads the CSV with an explicit schema, checks nulls/duplicates/invalid amounts, renames columns, adds `day`, `hour_of_day`, balance-error and `orig_emptied` columns, writes Parquet partitioned by `type` | ~20 s |
| `spark_jobs/analytics.py` | 7 Spark SQL queries (overview, type summary, hourly/daily activity, amount bands, balance patterns, repeat fraud destinations) published to MongoDB | ~25 s |
| `spark_jobs/train_model.py` | trains and evaluates the models, computes feature importance and a threshold curve, saves the model and the flagged test transactions | ~2.5 min |
| `serving/build_search_index.py` | reads the Parquet lake with DuckDB and writes `data/search.duckdb` with a deterministic `tx_id` and indexes on both account columns | ~40 s |

\*On a 16 GB Windows laptop, Spark `local[*]`.

`notebooks/eda.ipynb` contains the exploratory analysis behind these steps, with plots.

## The application

Three tabs sit next to the Overview (all need the server; the static site shows only the Overview).

### Explorer: millisecond search over 6.36M transactions

The Explorer page is a single account ID box. Typing shows matching accounts in a drop-down (up to 10, in id
order, via `GET /api/account-suggestions?prefix=C1305`, a range scan on the two account indexes, a few
milliseconds); pick one with the mouse or the arrow keys and Enter to see everything it sent and received. Every row is
scored by the fraud model and any transaction can be opened as a case. The API still accepts the extra filters (type,
amount, hour, fraud label, sort) on `/api/search`. The page no longer shows the speed comparison, but the same lookup
was measured four ways on a 16 GB Windows laptop (finding every transaction sent by one account):

| Method | Median |
|---|---|
| Spark SQL, full scan of the Parquet lake | 1,441 ms |
| DuckDB straight on the Parquet lake | 276 ms |
| DuckDB table, index switched off | 28 ms |
| **DuckDB table with the index (what the API uses)** | **2.5 ms** |

The API itself answers an account lookup in about 4–6 ms. Rerun the benchmark with
`python -m scripts.benchmark_search`. Two findings worth knowing: DuckDB's optimiser drops the
index when the query has an `ORDER BY` (12x slower), so account searches fetch the few matching
rows through the index and sort them in Python; and an `OR` across the two account columns is
slower than two separate lookups, so they are done separately. All query values are bound
parameters, and the only SQL text taken from a whitelist is the sort column.

### Cases: create, read, update, delete

An analyst opens a case from a transaction, moves it through a review workflow
(`new` → `investigating` → `confirmed_fraud` / `false_positive` → `closed`), assigns it, adds
notes and can delete it. Cases live in MongoDB with an audit history, and:

- status changes are validated and applied in one atomic update, so two concurrent changes cannot both win;
- there is at most one open case per transaction (a partial unique index);
- user text is wrapped in `$literal` in pipeline updates, because without it a note such as `$status` would be evaluated as a field reference (a test proves this);
- cases belong to an anonymous browser workspace (a random id kept in `localStorage`, sent as an `X-Owner` header; a header rather than a cookie because browsers block cookies in embedded pages), capped at 50 cases per workspace, and removed after 7 days without changes.

CRUD applies to this operational data, not to the 6.36M-row lake: the lake is immutable
analytical data that is rebuilt by the pipeline, and editing it in place would be the wrong
architecture.

### Upload: score your own file

Upload a CSV in the dataset's format. Locally the limits are 12 million rows or 1 GB; the
Docker image sets 100,000 rows or 25 MB for the public deployment (`UPLOAD_MAX_ROWS`,
`UPLOAD_MAX_BYTES`). The file is saved to disk and a background job streams it in 16 MB blocks:
each block is validated and scored with vectorised Arrow/numpy code and appended to the output
CSV, so only counters and the 500 riskiest rows stay in memory and memory use does not grow with
the file. The page shows a live progress bar. Rows that fail validation are listed with their
real file row numbers and do not stop the upload. If the file has an `isFraud` column the page
reports precision, recall and a confusion matrix. The scored CSV can be downloaded for 24 hours;
formula-like text in account names is neutralised so it cannot run in a spreadsheet.

Measured on a 16 GB Windows laptop, uploading the two generated demo files through the web page's API
(one file at a time; the model had never seen either file):

| File | Rows | Size | Scoring | Search index | Flagged | Precision / recall |
|---|---|---|---|---|---|---|
| `transactions_with_labels_8M.csv` | 8,000,074 | 565 MB | about 30 s | about 42 s | 28,561 | 51.8% / 92.1% |
| `transactions_without_labels_7M.csv` | 7,000,008 | 481 MB | about 35 s | about 38 s | 25,014 | not measurable (no labels) |

Uploading both at once roughly doubles each time. Scoring happens first; a second phase then builds a DuckDB search index for the file, and only after that is the file
explorable (about 70 s in total for the 8-million-row file).

### Demo data: two generated files (`scripts/generate_dataset.py`)

Real bank transactions are confidential, so the demo uploads are synthetic. The generator is seeded
(same seed, same file) and vectorised: 8 million rows take about 12 seconds.

```bash
python -m scripts.generate_dataset --rows 8000000 --labels --seed 7 --out data/samples/transactions_with_labels_8M.csv
python -m scripts.generate_dataset --rows 7000000 --seed 11 --out data/samples/transactions_without_labels_7M.csv
```

How the data is made:

1. **Genuine traffic.** Each row draws a transaction type from a fixed mix (CASH_OUT 35%, PAYMENT 34%,
   CASH_IN 22%, TRANSFER 8.4%, DEBIT 0.6%), an hour from a daily activity curve (quiet overnight) and an
   amount from a log-normal distribution per type. Accounts come from fixed pools of customers and
   merchants, a few receivers are far more popular than the rest, and balances stay consistent
   (balance after = balance before minus or plus the amount). About 0.4% of genuine transfers and
   cash-outs empty the sender's account on purpose, so there are look-alikes that are not fraud.
2. **Fraud events** (about 0.2% of rows). Account takeover: a victim's whole balance is moved to a mule
   account and cashed out within the hour. 20% are a direct cash-out, 15% take only part of the balance,
   and mule accounts are reused.
3. **Output.** Rows are ordered by time. With `--labels` the file has an `isFraud` column; without it the
   column is left out, like a feed that has no verdicts yet. The columns follow the PaySim layout.

Only the shape of the data (type mix, orders of magnitude) is borrowed from PaySim; no PaySim row is copied.
The built-in 500-row sample (`results/sample_upload.csv`, `python -m scripts.make_sample_upload`) comes from the
same generator. Because the model was trained on PaySim and these files are generated separately, the accuracy
shown on them is a fair test on unseen data, not a training-set number.

### Datasets: explore, analyse and open cases on your upload

The dataset picker at the top of the page chooses what the Overview, Explorer and Cases tabs work
on: the main ledger (the 6.36 million PaySim transactions) or any of your finished uploads. A finished upload is selected automatically.
Each upload gets its own search index (`/api/search?dataset=<id>`), its own overview computed with
SQL (`GET /api/datasets/{id}/overview`: type table, flag rate by hour, amount bands, score
histogram, accuracy if the file has `isFraud`, top flagged receivers), and cases can be opened from
its rows (the "transaction id" of an upload is the row number). Cases remember their dataset; the
Cases tab shows the selected dataset's cases, or all of them with the "all datasets" tick.
Uploads, their indexes and their cases expire like before (uploads after 24 hours).

The file is processed in a stream, so memory does not grow with the file size. Scoring itself is fast because rows are
scored in 25,000-row blocks on several threads: 426,000 rows/s, against 38,000 rows/s when the same rows are scored as
one big array.

Scoring in the application uses the Random Forest exported from Spark's model files and
evaluated with numpy (`backend/app/forest.py`), not Spark itself. It gives the same
probabilities as Spark (tested on all 2,424 scored test transactions, maximum difference 0.00005)
and means the server needs no Java.

## Findings

- **Fraud only occurs in TRANSFER (0.77%) and CASH_OUT (0.18%)** transactions. The other
  three types have no fraud at all. Frauds follow a take-over pattern: transfer the victim's
  balance to a controlled account, then cash it out.
- **The existing rule (`isFlaggedFraud`) flagged only 16 of 8,197 frauds** (0.2%).
- **Fraud volume is constant through the day** (about 270–370 per hour slot), while
  legitimate activity drops at night. As a result, **22% of transactions between 4:00 and
  6:00 are fraudulent**, compared with under 0.1% in business hours.
- **97.7% of frauds empty the sender's account**, compared with 42.7% of legitimate
  transfers/cash-outs. In 49.7% of frauds the receiver's recorded balance stays at 0 even
  though money arrived (0.06% for legitimate transactions).
- Fraud amounts are larger (median 442k vs 171k) and are capped at 10M: 287 frauds are
  exactly 10,000,000.
- **43 receiver accounts got more than one fraudulent transaction** (86 frauds). These are
  candidates for mule-account investigation.
- Data quality: no nulls or duplicates. 16 zero-amount rows (all CASH_OUT, all labelled
  fraud) were removed as invalid.

## Fraud detection model

Training data: 2.77M TRANSFER and CASH_OUT transactions (all other types have no fraud),
split 70/30 into training and test sets (seed 42).

Features: `is_transfer`, `amount`, sender and receiver balances before/after,
`error_balance_orig`, `error_balance_dest`, `hour_of_day`.

Fraud is 0.3% of this data, so accuracy is not meaningful: a model that never predicts fraud
is 99.7% accurate. The models are compared on precision, recall, F1 and area under the
precision-recall curve.

Results on the 831,437-row test set (2,407 frauds):

| Model | Precision | Recall | F1 | AUC-PR | Frauds caught | False alarms |
|---|---|---|---|---|---|---|
| Existing rule (`isFlaggedFraud`) | 1.000 | 0.002 | 0.003 | – | 4 / 2,407 | 0 |
| Logistic Regression (class-weighted) | 0.043 | 0.909 | 0.083 | 0.549 | 2,189 / 2,407 | 48,466 |
| **Random Forest** (60 trees, depth 12) | **0.993** | **0.998** | **0.995** | **0.998** | **2,401 / 2,407** | **17** |

- Logistic Regression catches most fraud, but with class weighting it raises about 20 false
  alarms for every real fraud. The relationship between balances and fraud is not linear.
- Random Forest is the selected model. The most important features are `new_balance_orig`
  (0.40), `error_balance_orig` (0.19) and `amount` (0.11).
- The 6 frauds it missed all have a sender balance recorded as 0 before and after, so the
  balance features carry no signal for them.
- Precision and recall stay above 0.99 for alert thresholds from 0.2 to 0.7, so the result
  isn't sensitive to the 0.5 cut-off.

## Running the project

Requires Python 3.10+.

### Dashboard only (works right after cloning)

The pipeline's results are committed in `results/` and the trained model in `models/`, so
the dashboard runs without downloading the data:

```bash
git clone https://github.com/JayQuery-007/bank_transaction_analysis.git
cd bank_transaction_analysis
python -m venv venv
venv\Scripts\activate            # macOS/Linux: source venv/bin/activate
pip install -r requirements.txt
python run.py
```

Open http://localhost:8000. No Java is needed to run the dashboard. What works depends on what is present:

| You have | You get |
|---|---|
| nothing extra | Overview (reads `results/*.json`) and the transaction scoring form |
| MongoDB on `localhost:27017` (or `MONGO_URI`) | also Cases and Upload |
| `data/search.duckdb` (built by the pipeline, not in Git) | also the Explorer |

### Full pipeline (rebuild everything from the raw data)

Needs **Java 17** (`JAVA_HOME` set, or `java` on the PATH) and a
[Kaggle API token](https://www.kaggle.com/settings) in `~/.kaggle/`. Alternatively, download
the CSV manually and save it as `data/raw/paysim.csv`.

```bash
python run_pipeline.py
```

Start MongoDB first if you want the results stored there. On Windows, `.\start.ps1` starts
a local MongoDB from `.\mongodb\` (if present) and then the dashboard.

### Tests

```bash
pip install -r requirements-dev.txt
pytest
```

Over 110 tests: scorer parity with Spark's stored probabilities, search results checked against
an independent pyarrow scan of the lake, SQL-injection and validation cases, the full cases
lifecycle (including isolation between workspaces and the `$literal` protection), uploads
(malformed rows, limits, formula injection, path traversal), the hosting download logic and the
deploy script. Tests that need MongoDB or the lake skip themselves when those are missing, and
MongoDB tests use their own throwaway database, never `bank_analytics`.

### Hosting

Two deployments, for different needs.

**Full application on a Hugging Face Docker Space** (search, cases, upload). Needs a Hugging Face
PRO subscription (Docker Spaces are not free) and a free MongoDB Atlas cluster. The image has no
Java or Spark (about 280 MB of RAM at runtime) and downloads the search index from a dataset
repo. One-time setup is described at the top of `deploy/deploy_space_app.py`. Your Atlas
connection string stays in your own terminal and is stored as a Space secret by the script:

```bash
hf auth login
$env:MONGO_URI = "mongodb+srv://..."          # PowerShell; your Atlas connection string
python deploy/deploy_space_app.py --dry-run   # checks everything, changes nothing
python deploy/deploy_space_app.py             # uploads the index and the app, waits for the build
```

The index is uploaded to a private dataset repo by default. Check the PaySim licence on Kaggle
before using `--public-index`, because a public search over every row is a form of republishing.
The anonymous workspaces, the caps on cases, uploads and notes, and the expiry of old data
exist because the hosted site accepts writes from anyone.

**Read-only showcase on a free static Space** (the live link above).
`deploy/build_static.py` copies the frontend and `results/*.json` into `site/` and exports
the trained Random Forest's 60 trees from Spark's model files to JSON. `frontend/forest.js`
then scores transactions in the browser with the same logic as Spark MLlib. The build
checks the export against Spark's stored probabilities for all 2,424 scored test
transactions, and it matches exactly.

```bash
hf auth login                   # one-time, signs in to Hugging Face
python deploy/deploy_hf.py      # builds site/ and uploads it to the Space
```

The static build hides the Explorer, Cases and Upload tabs, because they need a server.
The `Dockerfile` also runs on any other container host (Render, Railway, a VM) with about 1 GB
of RAM, the search index file and a `MONGO_URI`.

### Running Spark on Windows

Spark's local file writes call Hadoop native helpers (`winutils.exe`, `hadoop.dll`) on
Windows, which aren't distributed by Apache. Instead of downloading unofficial binaries, the
project includes a small Hadoop `FileSystem` subclass (`spark_jobs/winfs/src`, compiled into
`winfs.jar`) that uses plain Java file operations. `spark_jobs/common.py` enables it only
on Windows. The jobs also avoid Python UDFs, because PySpark's Python worker processes crash
on Windows with Python 3.12+.

## Limitations and future work

- PaySim is simulated. Its balance bookkeeping for fraudulent transactions is distinctive,
  which is why the balance-error features work so well. On real data, expect lower scores
  and more reliance on behavioural history.
- Customers almost never repeat in PaySim (6.35M distinct senders in 6.36M rows), so
  per-customer behaviour features (spending history, velocity) aren't possible here.
- The pipeline is batch. A natural extension is streaming new transactions through Kafka
  and scoring them with Spark Structured Streaming using the saved model.
- Runs on Spark in local mode; the same jobs would run unchanged on a cluster with the data
  in HDFS or object storage.
